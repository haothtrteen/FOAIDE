# 05 · 许可证合规

> 组件许可边界、双许可策略、CLA、分发合规检查清单
>
> **核心原则**：许可证红线不可碰。每引入一个新依赖，必须过本文的检查清单。

## 一、项目许可架构

```
┌─────────────────────────────────────────────────────────┐
│                    官方 App APK                          │
│  ┌───────────────────────────────────────────────────┐  │
│  │  专有增值层（商城客户端、加固入口、云部署 Agent）   │  │
│  │  → 专有许可，仅官方构建包含                        │  │
│  └───────────────────────┬───────────────────────────┘  │
│                          │ JSON-RPC / 进程隔离           │
│  ┌───────────────────────▼───────────────────────────┐  │
│  │  AGPL 开源核心（编辑器、构建编排、插件宿主）       │  │
│  │  → AGPL-3.0                                        │  │
│  └───────────────────────┬───────────────────────────┘  │
│                          │ fork/exec                    │
│  ┌───────────────────────▼───────────────────────────┐  │
│  │  proot 二进制（独立进程）                          │  │
│  │  → GPL-2.0，附源码获取链接                         │  │
│  ├───────────────────────────────────────────────────┤  │
│  │  Debian rootfs                                    │  │
│  │  → 自由软件混合（各组件各自许可）                   │  │

│  │  → GPLv2 with Classpath Exception                │  │
│  ├───────────────────────────────────────────────────┤  │
│  │  aapt2 / zipalign（ARM64 社区构建版）             │  │
│  │  → Apache-2.0（AOSP 源码）                        │  │

│                                                           │

│  - Android cmdline-tools → Google SDK ToS               │

│  - Gradle 发行版 → Apache-2.0（下载不分发）             │
└─────────────────────────────────────────────────────────┘
```

## 二、双许可策略

### 核心代码（app-core 仓库）

- **社区版**：AGPL-3.0，开源，任何人可自由使用、修改、分发；
- **商业授权**：企业或个人需要在闭源产品中使用核心代码时，购买商业授权。

### 版权归属

- 你自己写的代码：100% 归你，可自由决定许可方式；
- 外部贡献代码：**必须签 CLA** 后才能合并，否则你无权将其纳入商业授权版。

### CLA 要点（建议用"宽许可 + 保留版权"模式）

- 贡献者保留版权；
- 授予项目方"在 AGPL 和商业条款下同时分发贡献"的宽许可；
- 不要求版权转让（社区接受度更高）；
- 用 CLA-assistant 等工具自动化签名流程。

## 三、引入新依赖检查清单

每添加一个新依赖（Flutter 插件、原生库、二进制工具、npm 包……），按顺序检查：

1. **确认许可证**：查 LICENSE 文件或 pub.dev / maven 页面的 license 字段；
2. **对照下表判断兼容性**：

| 依赖许可证 | 能否进入 AGPL 核心 | 能否进入专有增值层 | 能否内置分发 | 备注 |
|---|---|---|---|---|
| MIT / BSD / Apache-2.0 | ✅ | ✅ | ✅ | 宽松许可，全兼容 |
| LGPL-2.1 / LGPL-3.0 | ✅ | ⚠️ 动态链接可，静态链接需谨慎 | ✅ | 以独立库（.so/.jar）形式链接，不改源码 |
| GPL-2.0 / GPL-3.0 | ✅ | ❌ 不能直接链接 | ⚠️ 独立进程可 | 必须进程隔离 + 附源码链接 |
| AGPL-3.0 | ✅ | ❌ | ✅ | 与核心同许可 |
| MPL-2.0 | ✅ | ✅（文件级 copyleft） | ✅ | 只要求修改的 MPL 文件开源 |
| PolyForm NC / BSL | ❌ | ⚠️ 增值层可用 | ⚠️ | 非 OSI，不能进开源核心 |
| Google SDK ToS | ❌ | ❌ | ❌ **绝对不能内置** | 用户首次运行自取 |
| 专有 / 商业 | ❌ | ✅ | 看授权条款 | 只能进专有增值层 |

3. **如果是 GPL 组件**：确认是以独立进程形式调用，还是动态链接进 App 进程——后者会传染；
4. **如果是 Google SDK 组件**：一律"用户首次运行自取"，不能放进安装包；
5. **记录到 THIRD-PARTY-NOTICES**：每个依赖的名称、版本、许可证、来源 URL、对应源码链接（GPL 类需要）。

## 四、常见许可边界判定

### proot（GPL-2.0）是否会传染 App？

- **进程隔离调用（Process.start）**：不传染。FSF 明确：主程序用 fork/exec 调用插件且无紧密通信，插件是独立程序 [$TRAE_REF](https://gnu.ac.cn/licenses/gpl-faq.html)。
- **App 内链接 proot 库**：会传染，不要这么做。
- **分发要求**：必须提供 proot 对应版本的完整源码获取方式（关于页放链接即可）。

### Flutter SDK（BSD）可以内置吗？

可以。BSD 许可允许自由分发，只需保留版权声明。

### sora-editor（LGPL-2.1）能在专有版里用吗？

- **作为 .aar 动态依赖链接**：可以，LGPL 允许专有软件动态链接 LGPL 库；
- **要求**：用户能替换 LGPL 组件（理论上需提供重新链接的方式，移动端实践中以提供库的源码 + 版本信息为准）；
- **更安全的选择**：用 MIT 许可的 `re_editor`，无任何传染风险。

### 第三方专有插件能否接入 AGPL 宿主？

- **进程隔离 + JSON-RPC**：可以，插件是独立程序；
- **直接链接宿主 SDK（同进程）**：不行，AGPL 会传染插件；
- **因此插件 SDK 的架构必须是独立进程模式**。

## 五、分发合规检查（发版前必过）

发布 community flavor（上 F-Droid / GitHub Releases）前：

- [ ] `LICENSE` 文件存在且为 AGPL-3.0 全文
- [ ] `THIRD-PARTY-NOTICES` 文件包含所有第三方组件的许可声明
- [ ] 所有 GPL 组件（proot 等）都有源码获取链接
- [ ] 不包含任何 Google SDK 专有组件（cmdline-tools、android.jar 等）
- [ ] 不包含专有增值层的代码
- [ ] `pubspec.lock` 中所有依赖的许可证都已核查
- [ ] 原生 `build.gradle` 中所有依赖的许可证都已核查
- [ ] ScanCode 扫描报告中无红色（未知 / 不兼容）项
- [ ] 关于页显示完整的开源许可列表

发布 official flavor（官网 / 应用商店）前，在以上基础上增加：

- [ ] 专有增值层代码未进入 community flavor（通过 flavor 隔离）
- [ ] 商标使用符合品牌规范
- [ ] 商城 ToS、隐私政策、用户协议等法律文件齐全
- [ ] 支付合规（国内 ICP / 海外支付主体）
