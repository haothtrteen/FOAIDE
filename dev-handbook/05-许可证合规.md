## 二、双许可策略

### 核心代码（app-core 仓库）

- **社区版**：AGPL-3.0，开源，任何人可自由使用、修改、分发；
- **商业授权**：企业或个人需要在闭源产品中使用核心代码时，购买商业授权。

### 版权归属

- 你自己写的代码：100% 归你，可自由决定许可方式；
- 外部贡献代码：**必须签 CLA** 后才能合并，否则你无权将其纳入商业授权版。

### CLA 要点（建议用"宽许可 + 保留版权"模式）

- 贡献者保留版权；
- 授予项目方"在 AGPL 和商业条款下同时分发贡献"的宽许可；
- 不要求版权转让（社区接受度更高）；
- 用 CLA-assistant 等工具自动化签名流程。

## 三、引入新依赖检查清单

每添加一个新依赖（Flutter 插件、原生库、二进制工具、npm 包……），按顺序检查：

1. **确认许可证**：查 LICENSE 文件或 pub.dev / maven 页面的 license 字段；
2. **对照下表判断兼容性**：

| 依赖许可证 | 能否进入 AGPL 核心 | 能否进入专有增值层 | 能否内置分发 | 备注 |
|---|---|---|---|---|
| MIT / BSD / Apache-2.0 | ✅ | ✅ | ✅ | 宽松许可，全兼容 |
| LGPL-2.1 / LGPL-3.0 | ✅ | ⚠️ 动态链接可，静态链接需谨慎 | ✅ | 以独立库（.so/.jar）形式链接，不改源码 |
| GPL-2.0 / GPL-3.0 | ✅ | ❌ 不能直接链接 | ⚠️ 独立进程可 | 必须进程隔离 + 附源码链接 |
| AGPL-3.0 | ✅ | ❌ | ✅ | 与核心同许可 |
| MPL-2.0 | ✅ | ✅（文件级 copyleft） | ✅ | 只要求修改的 MPL 文件开源 |
| PolyForm NC / BSL | ❌ | ⚠️ 增值层可用 | ⚠️ | 非 OSI，不能进开源核心 |
| Google SDK ToS | ❌ | ❌ | ❌ **绝对不能内置** | 用户首次运行自取 |
| 专有 / 商业 | ❌ | ✅ | 看授权条款 | 只能进专有增值层 |

3. **如果是 GPL 组件**：确认是以独立进程形式调用，还是动态链接进 App 进程——后者会传染；
4. **如果是 Google SDK 组件**：一律"用户首次运行自取"，不能放进安装包；
5. **记录到 THIRD-PARTY-NOTICES**：每个依赖的名称、版本、许可证、来源 URL、对应源码链接（GPL 类需要）。

### 历史案例：Kadb / spake2-java（2026-09-17 引入，同日移除）

> 保留这一节不是为了考古，而是因为下面每一条坑**换一批依赖还会再踩一次**。

**Kadb 实际解析出的传递依赖**（读 `kadb-android-2.1.3.pom` 得到，许可证已逐一核实）：

| 传递依赖 | 版本 | 许可证（核实方式） | 判定 |
|---|---|---|---|
| okio-jvm | 3.17.0 | Apache-2.0（POM `<licenses>`） | ✅ |
| androidx.documentfile | 1.1.0 | Apache-2.0（AOSP 标准） | ✅ |
| HiddenApiBypass | 6.1 | Apache-2.0（POM `<licenses>`） | ✅ |
| kotlinx-coroutines-core-jvm | 1.10.2 | Apache-2.0 | ✅ |
| bcprov-jdk18on / bcpkix-jdk18on | 1.83 | Bouncy Castle Licence（**MIT 风格**，已读官网正文） | ✅ |
| **spake2-java** | 1.0.5 | **GPL-3.0**（已读 GitHub `LICENSE`） | ⚠️ 见下节 |

> 上表为 **Kadb 2.1.1** 的解析结果。若升到 2.1.3，spake2-java 变 1.1.1、
> Bouncy Castle 变 1.84、kotlin-stdlib 变 2.4.0——**版本一变必须重跑本节核查**。

> 传递依赖不是"免费"的：Bouncy Castle 两个包合计会显著增加 dex/method 数，
> 若将来要做体积优化，可评估用 Android 自带 `Conscrypt` 替代（需改 Kadb 源码，不建议）。

**Kadb 的间接上游**（均在 Apache-2.0 或双许可下，Kadb 仓库整体以 Apache-2.0 发布）：

| 上游 | 许可证 | 说明 |
|---|---|---|
| [Dadb](https://github.com/mobile-dev-inc/dadb) | Apache-2.0 | Kadb 的主要来源（Kadb 有 "Merge commit from Dadb source" 提交） |
| [libadb-android](https://github.com/MuntashirAkon/libadb-android) | GPL-3.0-or-later **或** Apache-2.0（**双许可**） | ⚠️ Kadb 取的是 **Apache-2.0** 分支。若将来改为直接依赖 libadb-android，必须显式选择 Apache-2.0，否则 GPL-3.0 会要求源码提供义务（与 AGPL 仍兼容，但需附 NOTICE） |
| [spake2-java](https://github.com/Flyfish233/spake2-java) | **GPLv3** ⚠️ | 配对用的 SPAKE2+ 实现。**注意：Kadb 自身是 Apache-2.0，但它把这个 GPLv3 库作为 `api` 传递依赖带进来**（坐标 `com.github.Flyfish233:spake2-java:1.1.1`） |

**判定依据**：第三节表中「MIT / BSD / Apache-2.0 → ✅ 可进 AGPL 核心 / ✅ 可内置分发」。
Apache-2.0 与 AGPL-3.0 单向兼容（Apache-2.0 代码可并入 AGPL-3.0 作品，整体按 AGPL-3.0 分发），
需在 `THIRD-PARTY-NOTICES` 中保留 Apache-2.0 的 NOTICE 与专利条款声明。

### ⚠️ 连带影响：spake2-java（GPLv3）会进入 APK

引入 Kadb 会**连带把 GPLv3 的 spake2-java 静态链进 APK**，这是必须履行的义务：

| 项 | 处理 |
|---|---|
| 能否进 AGPL 核心 | ✅ 可以（GPLv3 §13 明确允许与 AGPLv3 作品合并，整体按 AGPLv3 分发） |
| 能否进专有增值层 | ❌ **绝对不行**——若将来有专有版，此依赖必须先摘除 |
| 义务 | 1) `THIRD-PARTY-NOTICES` 必须列出 spake2-java 及其 GPLv3 声明；2) 必须提供**对应源码链接**（GPL 要求）；3) 其自身 Credits 里的 `Curve25519-java`（GPL-3.0）、`EdDSA-Java`（CC0）、BoringSSL SPAKE25519（MIT）也应一并提及 |
| 进程隔离？ | ❌ 不适用——它是库调用，直接进 App 进程。这属于「静态链接 GPL 组件」，在 AGPL 主许可下合规，但**绝不可用于专有分发** |

> **教训**：本节第一版误把 spake2-java 当作「随 Kadb 以 Apache-2.0 分发」，是只看上游 README 未查
> 该库自己 LICENSE 的结果。规则 1「查 LICENSE 文件」必须**对每个传递依赖**都执行，不能只看直接依赖。

**另一个现实问题**：`com.github.Flyfish233:spake2-java` 是 **JitPack 独占**
（Maven Central / 阿里云 public 均 404），必须在仓库列表里显式加 `https://jitpack.io`。

**已采用的解法（2026-09-17）：从远端解析中排除 + 本地 vendor jar。**

`app/build.gradle.kts`：

```kotlin
implementation("com.flyfishxu:kadb:2.1.1") {   // 版本为何钉死见下
    exclude(group = "com.github.Flyfish233", module = "spake2-java")
}
implementation(files("../libs/spake2-java-1.0.5.jar"))
```

产物由 `app/tools/vendor_kadb.sh` 落地到 `android/libs/`：
`kadb-android-2.1.1.aar`（阿里云）+ `spake2-java-1.0.5.jar`（JitPack）。
注意：① **spake2-java 在 JitPack 只发 jar、不发 aar**（AAR 路径 404），脚本已做回落；
② spake2-java 版本**随 Kadb 版本走**（2.1.1→1.0.5，2.1.3→1.1.1），升 Kadb 必须同步改。

**⚠️ 本地 vendor 的代价：传递依赖要手工补齐（实测踩到）**

spake2-java 的 JitPack POM 里声明了两个 `scope=runtime` 依赖：

```
cafe.cryptography:ed25519-elisabeth:0.1.0      (MIT)
cafe.cryptography:curve25519-elisabeth:0.1.0   (MIT)
```

用本地 jar 顶替后，**jar 不带 POM**，这两个依赖不会被引擎解析。后果不是编译报错，
而是更阴的两级故障：

1. R8（`minifyReleaseWithR8`）报 `Missing class cafe.cryptography.curve25519.*` → 构建失败；
2. 即便关掉 R8 侥幸编出来，**运行期一配对就 `NoClassDefFoundError`**
   （`Spake2Context.<clinit>` 里就引用了 `CompressedEdwardsY`）。

已在 `build.gradle.kts` 显式补上这两个依赖。

> **规则补充（写进第三节 checklist）**：凡是用 `files(...)` 本地 vendor 替换 Maven 依赖，
> 必须**手工把被替换件的 POM 依赖全部补齐**，并逐项走一遍许可证核查
> （本例两个是 MIT，侥幸都是宽松许可；换一批就可能带进 copyleft）。

**另一个坑：Kadb 不能升到 2.1.2+。** `kadb-android` 的 AAR 元数据
`META-INF/com/android/build/gradle/aar-metadata.properties` 写着 `minCompileSdk`，
2.1.2 / 2.1.3 / 2.1.4 都是 **37**，而本机 SDK 只装了 android-36、AGP 9.1.0 上限也是 36 →
构建报 "compileSdk of at least 37" 直接失败。**2.1.1 的 `minCompileSdk=36` 是最高可用版本**，
且其 API（`pair`/`create`/`shell`/`install`）与 2.1.3 逐签名一致（已 `javap` 核对），功能无损。
要升就得先备好 android-37 平台 + 支持 37 的 AGP。

排查这类问题的快捷手段（不用等完整构建）：

```bash
unzip -p some.aar META-INF/com/android/build/gradle/aar-metadata.properties | grep minCompileSdk
```

**过程中的一个坑（值得记下来）**：第一反应是往 `~/.gradle/init.gradle` 的
`beforeSettings { settings.dependencyResolutionManagement.repositories { ... } }` 里加 jitpack，
**结果完全没生效**——构建日志里 Gradle 只尝试了 `dl.google.com` 与 `repo.maven.apache.org`。
原因：本项目 `settings.gradle.kts` **没有**声明 `dependencyResolutionManagement`，
`RepositoriesMode` 走默认的 `PREFER_PROJECT`，于是 `app/build.gradle.kts` 自带的
`repositories { google(); mavenCentral(); ... }` 胜出，init 脚本里给 settings 配的仓库被整段忽略。

> 结论：改镜像/加仓库时，**先看 `settings.gradle.kts` 是否声明了 `dependencyResolutionManagement`**；
> 没声明就别指望 init.d 里的 settings 级配置生效，得改工程里的 `repositories`。
> （本项目最终干脆绕开仓库问题：能 vendor 的就 vendor，构建不再依赖 JitPack 可用性。）

**结局（2026-09-17）**：AVF 路线因设备不支持暂停、原生 arm64 路线不再需要 adb，
于是整块删除：`AdbWireless.kt` / `adb_bridge.dart` / `adb_page.dart` /
`tools/vendor_kadb.sh` / `android/libs/*.aar|jar`，`build.gradle.kts` 依赖清空的
同时也在文件顶部写下了"为什么不能有依赖"。**删掉一个 GPL 传递依赖，比合规地
带着它走要省事得多**——这是本次最大的收获。

**⚠️ 注意（与 Google SDK 无关，但易混淆）**：Kadb 只是 adb **客户端协议**实现，
不含任何 Google SDK 二进制；adb 协议本身（AOSP platform/system/core）为 Apache-2.0，
不触发「Google SDK 组件一律用户自取」那条规则。

## 四、常见许可边界判定

### proot（GPL-2.0）是否会传染 App？

- **进程隔离调用（Process.start）**：不传染。FSF 明确：主程序用 fork/exec 调用插件且无紧密通信，插件是独立程序 [$TRAE_REF](https://gnu.ac.cn/licenses/gpl-faq.html)。
- **App 内链接 proot 库**：会传染，不要这么做。
- **分发要求**：必须提供 proot 对应版本的完整源码获取方式（关于页放链接即可）。

### Flutter SDK（BSD）可以内置吗？

可以。BSD 许可允许自由分发，只需保留版权声明。

### sora-editor（LGPL-2.1）能在专有版里用吗？

- **作为 .aar 动态依赖链接**：可以，LGPL 允许专有软件动态链接 LGPL 库；
- **要求**：用户能替换 LGPL 组件（理论上需提供重新链接的方式，移动端实践中以提供库的源码 + 版本信息为准）；
- **更安全的选择**：用 MIT 许可的 `re_editor`，无任何传染风险。

### 第三方专有插件能否接入 AGPL 宿主？

- **进程隔离 + JSON-RPC**：可以，插件是独立程序；
- **直接链接宿主 SDK（同进程）**：不行，AGPL 会传染插件；
- **因此插件 SDK 的架构必须是独立进程模式**。

## 五、分发合规检查（发版前必过）

发布 community flavor（上 F-Droid / GitHub Releases）前：

- [ ] `LICENSE` 文件存在且为 AGPL-3.0 全文
- [ ] `THIRD-PARTY-NOTICES` 文件包含所有第三方组件的许可声明
- [ ] 所有 GPL 组件（proot 等）都有源码获取链接
- [ ] 不包含任何 Google SDK 专有组件（cmdline-tools、android.jar 等）
- [ ] 不包含专有增值层的代码
- [ ] `pubspec.lock` 中所有依赖的许可证都已核查
- [ ] 原生 `build.gradle` 中所有依赖的许可证都已核查
- [ ] ScanCode 扫描报告中无红色（未知 / 不兼容）项
- [ ] 关于页显示完整的开源许可列表

发布 official flavor（官网 / 应用商店）前，在以上基础上增加：

- [ ] 专有增值层代码未进入 community flavor（通过 flavor 隔离）
- [ ] 商标使用符合品牌规范
- [ ] 商城 ToS、隐私政策、用户协议等法律文件齐全
- [ ] 支付合规（国内 ICP / 海外支付主体）
