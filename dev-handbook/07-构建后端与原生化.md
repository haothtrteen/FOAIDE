# 七、构建后端：QEMU 转译 vs 原生 arm64

> 2026-09-18 建立。背景：AVF（Android 虚拟化框架）路线因设备不支持暂停，
> 提速方向改为"把构建链里的宿主二进制逐个换成 aarch64 原生"。
> 本文说明**两套后端如何共存、原生化走到哪一步、还差什么**。

## 一、为什么会有两套后端

Flutter 官方 Linux SDK 与 Android build-tools 只发布 **x86_64 宿主二进制**。
在 aarch64 的 proot 容器里直接 exec 会 `Exec format error`。可选解法只有两种：

| 方案 | 做法 | 代价 |
|---|---|---|
| **转译**（现状） | 容器内装 qemu-user-static，把 x64 二进制换成"qemu 转发脚本" | 每个宿主工具每次执行都要动态翻译，AOT 编译阶段最慢 |
| **原生**（新增） | 直接换成 aarch64 版的同名二进制 | 无需翻译；但 Google 不发布，得找第三方构建 |

两者**不是替代关系，是可切换的并行后端**——同一个路径（如
`$SDK/build-tools/36.0.0/aapt2`）里放的是转发脚本还是 arm64 ELF，决定了当下走哪条路。
这也是为什么顺序门控现在是 `qemu 已装 || native 已装`，而不是只认 QEMU。

## 二、原生化到哪一步了（逐项）

| 组件 | 现状 | 能否原生 | 怎么做 |
|---|---|---|---|
| `java` / `javac` | JDK 有 aarch64 Linux 发行版 | ✅ | 换 JDK 包（当前装的就是 arm64 版则无需动） |
| `gradle` / `d8` / `R8` | 纯 JVM | ✅ 天然原生 | — |
| `dart` | Dart SDK 有 linux_arm64 发行版 | ✅ | 换 dart-sdk；**但见下方"快照"一项** |
| `flutter_tools.snapshot` | x64 app-jit 快照（内含机器码） | ⚠️ | 必须让 arm64 dart **重新生成**，否则报 `Snapshot not compatible` |
| `aapt2` / `aidl` / `zipalign` / `split-select` | Google 只发 x86_64 | ✅ | **已实现**：Commit451 的 MIT arm64 构建，工具链页一键落位 |
| `gen_snapshot` | Google 只发 x86_64 | ⚠️ 唯一硬缺口 | **已实现导入通道**：用户自备 → 本地导入 → 校验 + 冒烟 |

## 三、架构体检（`lib/toolchain/native_arm64.dart`）

动手前先看清楚现状。体检是**只读**的，把每个关键二进制的 ELF Machine 与
DT_NEEDED 抓出来，UI 上一行一项：

- **Machine**：`dd` 读 ELF 头偏移 18 的 e_machine（不依赖 binutils）
  ——`0x3e`=x86-64、`0xb7`=aarch64、`0x28`=arm(32)；
- **DT_NEEDED**：有 `readelf` 就用 `readelf -d`（精确）；没有就退化为
  `grep -a` 字符串粗扫，并在 UI 上标注"粗扫"（minbase rootfs 不带 binutils，这是常态）；
- **链接类型判定**：DT_NEEDED 里出现无版本号的 `libc.so` / `libm.so` / `libdl.so`
  → **bionic**（Termux 系移植产物的指纹）；出现 `libc.so.6` → glibc；
- **QEMU 转发识别**：文件以 `#!` 开头且内含 `qemu` → 判定为转发脚本（说明这条还在转译）。

`NativeAudit.buildReady` 的判据（aidl / split-select 不计入，缺失不阻断普通构建）：
`dart` 是 aarch64 ELF **且** `dart --version` 报告 `linux_arm64`（快照架构匹配）
**且** gen_snapshot 有 aarch64 版 **且** aapt2 / zipalign 是 aarch64 ELF。

## 四、aapt2 等四个二进制的落位

来源：**Commit451/android-arm-build-tools**（MIT），用 AOSP Soong 在 Debian 12 上
交叉编译出 linux-glibc-arm64 的四个二进制——正是 AGP/Gradle 在一次普通 app 构建里
真正会 exec 的那四个（其余 apksigner/dx/d8 都是 Java，本来不挑架构）。

| 项 | 值 |
|---|---|
| tag | `platform-tools-36.0.0`（与本项目 SDK 装的 build-tools 36.0.0 同名，避免版本错配） |
| 文件 | `android-build-tools-36.0.0-linux-arm64-20260522.tar.xz` |
| 大小 / SHA-256 | 3,330,048 B / `c95050308f13fad7b73a06ce304f474363a2d6b5054f1834109f0e84d980b7fa` |
| 运行时要求 | glibc 2.36+ 与 GLIBCXX_3.4.30+ → rootfs 是 Debian 12 bookworm，满足 |

流程：竞速选源（GitHub 官方 + 两个第三方加速代理）→ 分段下载 → **SHA-256 校验**
→ 容器内解包（用 `find -name aapt2` 定位，不假设 tar 顶层目录名）→ 校验架构必须
`b700` → 备份原件为 `.foa-x64` → 覆盖 → 冒烟（`aapt2 version` / `zipalign`）。

两个设计细节：

1. **备份用 `cp` 而不是 `mv`**。QEMU 兼容层也在这条路径上留下 `.foa-real`
   （x64 原件）。用复制能保证两个后端各自的备份都完好，不会互相踩。
2. **AGP 9.x 必须写 `android.aapt2FromMavenOverride`**。AGP 9 起不用 SDK 里的
   aapt2，改从 Maven 拉 `com.android.tools.build:aapt2:<ver>:linux`（x86_64-only）。
   QEMU 后端与原生后端写的是**同一条路径**，只是内容不同——所以两个后端
   共用 `QemuCompat.writeAapt2Override()`。

> 关于第三方加速代理：它们是不受信任的中转，但下载后逐字节校验 SHA-256
> （值取自 GitHub API 的 asset digest），所以最坏情况只是"下载失败"，
> 无法注入错误内容。

## 五、gen_snapshot：唯一硬缺口

Google 不发布 linux-arm64 的 gen_snapshot，只能取第三方移植（如 Termux 系
Flutter aarch64 构建）。**本项目不提供自动下载**——体积 600MB+ 的 deb，
且沙箱内无法校验——只提供「用户自备文件 → 本地导入 → 校验 → 冒烟」通道。

导入流程（`NativeGenSnapshot.importFromLocalFile`）：

1. 拷到 `/opt/foa-native/gen_snapshot`；
2. 校验 e_machine 必须是 `b700`；
3. 读 ELF INTERP 判断链接类型，并据此给出**不同的失败提示**；
4. 实跑 `gen_snapshot --help` 冒烟；
5. **冒烟不过就当场删除**（连带原生侧的挂载自动失效，不留半吊子状态）。

### bionic 二进制必须让容器看见 /system 与 /apex

Termux 系二进制是 **bionic 链接**的：`INTERP=/system/bin/linker64`，libc.so 来自
`/apex/com.android.runtime/lib64/bionic`。而容器 rootfs 是 glibc 的 Debian，
没有 `/system`、`/apex` 时连解释器都找不到，报 `No such file or directory`
或 `CANNOT LINK EXECUTABLE ... library not found`。

原生侧按**落位标记**（`rootfs/opt/foa-native/gen_snapshot` 是否存在）自动追加：

```kotlin
// MainActivity.buildProotCmd()
if (File(rootfs, NATIVE_GEN_SNAPSHOT_REL).exists()) {
    for (p in NATIVE_BIONIC_BINDS) {   // /system /apex /linkerconfig
        if (File(p).exists()) { argv.add("-b"); argv.add(p) }
    }
}
// 同时 libraryPath() 追加 bionic 库搜索路径
//   /apex/com.android.runtime/lib64/bionic : /apex/com.android.art/lib64
//   : /system/lib64 : /vendor/lib64
```

仅新增挂载点，不动 rootfs 自身文件；Debian 程序不会去 `/system` 找库，无副作用。
未落位时行为与以前完全一致（两条 `if` 都走 false 分支）。

## 六、还没做的（以及为什么）

| 缺口 | 说明 |
|---|---|
| **dart arm64 + flutter_tools.snapshot 重建** | 换成 arm64 dart-sdk 后，x64 的 `flutter_tools.snapshot` 会报 `Snapshot not compatible`。需要让 arm64 dart 重新生成快照（`flutter` 工具自身支持，但要在容器内跑通且耗时长），或退化为从源码运行 flutter_tools。这是"全 arm64 构建"的最后一块拼图 |
| **impellerc / font-subset / const_finder** | 同为宿主工具，官方只发 x64；目前由 QEMU 兜底 |
| **adb** | 构建流程本身不需要 adb（`flutter build apk` 不装包），可不管 |

1. Commit451 的 tar.xz 能否在真机网络下下载（三个源竞速，任一通即可）；

## 八、Termux bionic 供应链核实（2026-09-18，WebFetch 逐包确认）

背景：评估「去 proot、App 层模仿 Termux 直跑」的可行性时，逐包核实了
Termux 主仓（termux-packages）的现货情况。**结论：bionic 版供应链几乎全现货，
纯原生路线从"主工程"降级为"组装工程"**。

### 8.1 现货清单（全部主仓官方包，非第三方 fork）

| 组件 | Termux 包 | 版本（2026-09 实查） | 证据 |
|---|---|---|---|
| JDK | `openjdk-17` / `openjdk-21` | 17.0.20 | build.sh：clang 交叉构建、`-D__ANDROID__=1`、依赖 libandroid-shmem/libandroid-spawn——真 bionic 构建 |
| dart | `dart` | 3.13.2 | build.sh：dart-lang/sdk 源码 `--arch arm64 --os android create_sdk`——**bionic dart + android 宿主 gen_snapshot 现货** |
| aapt2 / aidl / zipalign / aapt | `aapt`（源码 termux/android-build-tools） | 16.0.0.4-r2（已跟进 android-17.0.0_r1） | README "Supported Tools" 明列 aidl/aapt/aapt2/zipalign；Apache-2.0 |
| Gradle | `gradle` | 9.7.1（依赖 openjdk-21） | 平台无关 zip，可随项目 wrapper |
| d8 / dx | `d8` / `dx` | 主仓在列 | 目录清单 |
| kotlin / apksigner / apktool | `kotlin` / `apksigner` / `apktool` | 主仓在列 | 目录清单 |
| git / busybox / coreutils / tar / xz / unzip | 同名包 | 主仓在列 | 隐式依赖群全覆盖 |
| glibc 兼容 | `glibc-repo` | 官方 glibc 仓库 | 无 proot 跑 glibc 程序在 Termux 生态本就是被支持路径 |

### 8.2 剩余的真约束（只有一条是硬的）

1. **【硬】gen_snapshot × Flutter 引擎版本严格匹配**：Termux `dart` 3.13.2 与
   ImL1s flutter 3.44.0 都与本项目 SDK 3.47.4（engine 06a2e2a1）不同版本，
   gen_snapshot 产物与 libflutter.so 不匹配会启动崩溃（手册 02 §三）。
   三选一：a) FOA 的 Flutter SDK 版本锁定到 Termux 系能提供的版本；
   b) 推动社区出 3.47.4 移植；c) 自己从 engine 源码编（手册 7.2 路线 B，
   Termux dart 包已证明"Android 上从源码编 dart/engine 工具链"可行）。
2. **【软】split-select 无 bionic 现货**：termux/android-build-tools 四件里没有它。
   单 ABI 单 APK（abiFilters）场景不调用 split-select，影响极小，真机实测确认。
3. **【软】Termux prefix 硬编码**：deb 包 prefix = `/data/data/com.termux/files/usr`。
   对策：FOA 模仿 Termux 布局（`filesDir/termux/usr/...` + `PREFIX`/`LD_LIBRARY_PATH`
   环境变量重定向），或 wrapper 逐个包；termux-exec（LD_PRELOAD）作可选兜底。
4. **【软】deb 解包**：FOA 无 dpkg，deb = ar + tar，自带 mini 解包器即可
   （或直接引用 Termux apt 仓库 URL 按组件抓取）；版本要锁快照防滚动漂移。
5. **【软】aapt2 与 AGP 9.1 的版本代差**：AGP 期望 build-tools 36 系 aapt2，
   Termux 版本更新更激进，daemon 协议稳定，实测为准（`aapt2FromMavenOverride`
   机制已就位）。

### 8.3 对路线的影响

- 纯原生 PoC 材料全部换 Termux 现货：`dart --version`（bionic dart 直跑）、
  `java -version`（Termux JDK 直跑）、`aapt2 version`（bionic 四件套直跑）——
  都不再需要任何编译，PoC 只剩"解包 + 环境变量 + 直跑"三件事；
- 混合方案（现状）不受影响：proot 容器内的 Commit451 glibc 四件套照常；
  两路线可长期共存（后端枚举 qemu / native-容器 / native-bare）；
- 纯原生路线的独有收益：去掉 78MB rootfs、去掉 proot syscall 拦截开销
  （编译负载实测 10%~30%）、gen_snapshot 不再需要挂 `/system` `/apex`
  （bionic 是它的原生环境）。

## 九、native-bare 后端落地（2026-09-18，v0.1.0-alpha.28）

§八 供应链核实定调后，native-bare 作为**第三个后端**（proot 容器 / QEMU x64 /
termux 裸原生）正式落地。与既有后端并行共存、可切换、互不污染。

### 9.1 代码落点（谁负责什么）

| 文件 | 职责 |
|---|---|
| `lib/toolchain/termux_backend.dart` | `BuildBackend` 枚举 + `BackendPrefs`（filesDir/foa-backend.json 持久化，null=未选择）；`TermuxPaths`（路径唯一封装点）；`parsePackagesIndex`/`compareVersions`/`newest`（纯函数，单测覆盖）；`TermuxRepo`（4 镜像容错索引解析 + deb 直链）；`TermuxInstaller`（deb 安装 / Flutter 本地导入 / bare 冒烟 / 卸载） |
| `lib/env/proot_bridge.dart` | `exec`/`execStream` 增加 `{bool bare}` 透传 MethodChannel |
| `MainActivity.kt` | `bareEnvironment()`（TERM/HOME/TMPDIR/PREFIX/PATH/LD_LIBRARY_PATH/LD_PRELOAD/JAVA_HOME/GRADLE_USER_HOME/ANDROID_HOME/国内镜像注入）；`execBare()`（/system/bin/sh -c 双线程读流 + 超时）；`execStream(bare)` 分支 |
| `toolchain_page.dart` | 顶部 `_BackendSwitcher`（SegmentedButton）；**首次进入弹询问对话框并推荐**；`_TermuxCard`（JDK 17 / aapt 四件套 / Flutter 导入三组件 + 进度/冒烟/卸载） |
| `build_page.dart` | 双后端构建命令：termux 模式走 bare 通道 + 宿主路径（rootfsPath + 容器路径）+ flutter 全路径 + `aapt2FromMavenOverride` |

### 9.2 关键设计决策（为什么这么做）

1. **prefix 落在 rootfs 树内**（`<rootfs>/opt/foa-termux/usr`）而非 filesDir 独立目录：
   安装期要用容器里的 `dpkg-deb` 解包（宿主没有 ar/xz），容器路径与宿主路径
   是**同一物理目录**，解包结果零搬运；将来引入内置 busybox 解包器后只需改
   `TermuxPaths` 一处即可解耦 rootfs。
2. **安装期借用容器，执行期完全脱离容器**：deb 两种布局都识别（prefix 相对
   `bin/...` / 全路径 `data/data/com.termux/...`），解包后 `sed` 把
   `/data/data/com.termux/files/usr` 绝对路径改写为宿主 prefix（shebang 等
   文本文件），binary 交给 bionic linker 按 `LD_LIBRARY_PATH` 自行解析。
3. **架构无关资产跨后端复用**：Android SDK 的 jars/android.jar/许可、
   Gradle 缓存（`GRADLE_USER_HOME=rootfs/root/.gradle`，仓库 URL 两模式一致
   → Maven 依赖零重下）。
4. **构建命令的 termux 差异**：flutter 不在 PATH（用 `TermuxPaths.flutterHome`
   全路径）；环境用 Dart 口径 `envPrefix()` 再 export 一遍（与 Kotlin 注入
   双保险）；`-Pandroid.aapt2FromMavenOverride` 指 prefix 的 bionic aapt2
   （-P 优先级高于 gradle.properties，不污染工程文件）。
5. **git 是 termux 模式的硬前置**：容器 git 是 glibc 二进制，bare 直跑不了；
   ToolchainEnsure 的 apt 兜底只对 proot 模式有效。termux 模式构建前 Dart 侧
   检查 `prefix/bin/git`（bionic git 需通过 TermuxCard 安装），缺了快速失败。
6. **gradle wrapper 镜像改写 termux 模式走 Dart 文件 IO**：wrapper properties
   在 rootfs 树内宿主可写，不必经 shell。
7. **推荐逻辑（诚实原则）**：proot = 已真机验证 → 首选推荐；termux = 供应链
   核实过但链路未真机验证 → 明确标注实验性，不背书。

### 9.3 单测拦下的真 bug（门禁的价值案例）

`TermuxPaths.jdkHome/flutterHome/aapt2` 首稿写了 `'$prefix/...'`——静态方法名
在字符串插值里被当 **tear-off**（`Closure: ...`），拼出的"路径"是闭包的
toString。analyze 抓不到（合法语法），`termux_backend_test.dart` 的路径断言
当场拦截。教训：**静态方法拼路径一律 `'${method(...)}/...'`**。

### 9.4 termux 后端真机验证清单（衔接 §七，沙箱无法代验）

1. bare 冒烟三件套：`java -version` / `aapt2 version` / `flutter --version`
   （W^X + bionic linker + libtermux-exec 预载）；
2. `dpkg-deb -x` 解包 + 两种 deb 布局探测 + `com.termux` 路径改写条数；
3. bare 构建：`cd <host>/root/projects/<name>` → flutter 全路径 → gradle 起得来、
   aapt2 override 生效、产物落 build/app/outputs/flutter-apk；
4. Commit451 原生四件套在 bare 模式的可用性（与容器原生 aapt2 的取舍）；
5. bionic gen_snapshot 挂载豁免：不经 proot 时 `/system`/`/apex` 本就可见，
   验证版本匹配的 Flutter 导入包构建出的 APK 能安装并启动。

### 9.5 在线下载路线与慢速熔断（2026-09-18，v0.1.0-alpha.29，真机反馈驱动）

真机实测两个问题 → 两项改进：

**① Flutter bionic 的社区分发渠道核实**：Termux 主仓**没有** flutter 包
（Flutter 官方不支持 bionic host，进不了 apt 体系）。社区分发走 GitHub
releases：**ImL1s/termux-flutter-wsl**（fork 自 mumumusuc/termux-flutter），
WSL 交叉编译 engine+dart，`flutter_3.44.0_aarch64.deb`（666,366,556 B，
SHA256 b8af08d2…，2026-06-01 Android 16 实机验证 flutter build apk ✅）。
因为不在 apt 仓里，TermuxRepo 的 Packages 索引抓不到 → 新增
`TermuxFlutterRelease` 快照锁定 + `installFlutterOnline`：GitHub 直链 +
gh 加速代理（gh-proxy.com / ghfast.top / ghproxy.net，前缀拼接式）多源
竞速，8 分片并行，SHA256 校验后走与本地导入同一套容器解包落位；全部源
失败 → UI 提示回退本地导入。

**② 下载器慢速熔断**：原有熔断只覆盖"卡死"（stallTimeout 15s 无数据），
抓不住"涓流"（真机实测 16 KB/s 持续慢流——有数据就不算卡，永不换源）。
新增滑动窗口速度检测：窗口 ≥10s 且均速 <64KB/s → 判定镜像限速，
抛出换源续传（.p<i> 分片保留，续传代价仅重连）。阈值依据：教育网镜像
正常 ≥5MB/s、GitHub 直链国内 ≥200KB/s，64KB/s 远低于健康源下限。

下载机制全景（SdkDownloader）：4 分片轮流起步到不同镜像（i % n）→
64KB 探针竞速排序 → 每片三重保护：卡死熔断（15s 无数据）/ 慢速熔断
（10s 窗口 <64KB/s）/ 瞬时抖动同源重试（≤2 次）→ 全镜像耗尽才报错，
分片文件保留可断点续传。

### 9.6 构建后台保活：前台服务 + 通知进度（2026-09-18，v0.1.0-alpha.31）

需求：退出构建页/退到桌面后构建继续，通知栏可见进度，点通知回构建页。

**架构（三层）**：

1. **构建会话与页面解耦（`build_runner.dart`）**——根子在这里。原实现
   构建状态全是 BuildPage 的 State 字段，`dispose` 直接
   `execStreamStop` 杀构建（"离页即中止"防 gradle daemon 管道泄漏的
   历史决策）。改为全局单例 `BuildRunner`：状态（streamId/offset/lines/
   prog/hints/apkGuest）+ 执行逻辑（start/poll/finish/cancel）全搬进去；
   页面变薄视图，attach 时注入 `onUiChanged`/`onAutoScroll` 两个钩子，
   dispose 只解绑钩子不杀会话。重进页面（或点通知回来）无缝挂回，
   日志/进度/产物续显。
2. **原生前台服务（`BuildService.kt`）**：构建进程树是 App 进程的子进程，
   退后台后 App 优先级跌到 cached，随时被 LMK 连坐整树——幸存 dart
   孤儿还持 flutter 启动锁（Bug 420 源头）。前台服务把优先级抬到
   FOREGROUND。Dart `notifyStart` → startForegroundService；
   `notifyProgress` → 通知更新（Kotlin 侧再限频 800ms，Dart 侧按
   「阶段/百分比变化」节流，双保险防 gradle 刷屏打爆 NotificationManager）；
   `notifyStop` → 结果文案 + `stopForeground(false)` detach + stopSelf
   （通知留栏可滑除，点击回构建页看日志）。
3. **通知桥（`build_notify.dart`）**：复用 `dev.foa/proot` 通道
   （原生只反向 invoke 过 `navigate`，Dart setMethodCallHandler 不劫持
   正常调用）。不引 flutter_local_notifications——App 进程三方依赖
   归零是仓库原则（alpha.27 移除 Kadb 同因），通知三件套原生百行内做完。

**点击回跳的两条路径**：
- 前台：通知 contentIntent（singleTop + EXTRA_NAVIGATE）→ onNewIntent →
  `dartChannel.invokeMethod("navigate")` → FoaApp 注册的 onNavigate →
  根 navigatorKey push BuildPage；
- 冷启动：Dart handler 未注册，原生 `pendingNavigate` 暂存，Dart 首帧后
  `takeNavigate` 主动拉取。两条缺一不可，只做前台路径时冷启动点击会
  静默丢失。

**targetSdk 28 的两个红利**：① 前台服务无 foregroundServiceType 强制
（API 34+ 才要求，省掉 dataSync 的 6 小时限制）；② POST_NOTIFICATIONS
（Android 13+）对 targetSdk<33 的应用由系统自动授予，无需运行时申请
——但用户手动关通知仍可能（13+），Dart 侧 `notificationsEnabled` 检查
后 SnackBar 引导去设置，不阻断构建。

**边界**：从最近任务滑掉 App 仍会杀服务+进程树（Android 12+ 强制，
START_NOT_STICKY 也不重建——进程死了构建子树必死，重建无意义）。
"退出界面"（Home/锁屏/切应用）由前台服务覆盖。

### 9.7 项目工作台：点工程先进工作台不直接构建（2026-09-18，v0.1.0-alpha.33）

需求（模仿 FusionApp 风格参考图）：主界面点工程卡片 → 先进**项目工作台**
（`project_page.dart`），构建不再是一等入口——BuildPage 保留给通知回跳
与长按菜单直达。

**结构：侧边抽屉四区**（选中项薄荷绿圆角高亮）：

| 区 | 内容 | 关键实现 |
|---|---|---|
| 概览 | 图标卡 + pubspec 解析（name/description/version/依赖数）+ applicationId + 后端标签 + 快捷卡（写代码/打包） | `_readManifest` 正则提取 |
| 代码 | 内嵌 FileTree（根 = 容器 `/root/projects/<name>`）+ 顶栏「编辑器」按钮 | FileTree 加 `initialDir`；EditorPage 加 `initialDir`/`initialPath`（initState addPostFrameCallback 打开文件） |
| 清单 | 应用名/包名**只读** + 版本名/版本代码**可编辑**（保存正则替换 pubspec `version: $vn+$vc` 行）+ 依赖/权限展示 | 版本名校验 `^\d+\.\d+\.\d+([\-+.\w]*)?$`；dirty 才允许保存 |
| 打包 | BuildRunner 快照面板：idle 配置卡 → building 进度卡（阶段/百分比/进度条/耗时/取消）+ 最近 30 行日志 → 结果卡（安装/查看详情 → BuildPage） | 自带 `_uiTimer` 500ms 轮询 |

**三个设计决策**：

1. **清单只读边界**：applicationId 不可编辑——改包名 = 变成另一个应用
   （旧包覆盖安装失败、签名/数据全断）；label 不可编辑——它在
   AndroidManifest 的 application/activity 多处出现，正则替换易误伤；
   版本名/版本代码是 pubspec 单一来源（`version:` 一行），写回安全。
   编辑版本后走正常构建，产物 versionName/Code 即新值。
2. **打包区不碰 `onUiChanged`**：BuildRunner 只有一个 onUiChanged 单回调
   槽位，BuildPage attach 时占用；工作台打包区若也注册会互踩（两页面
   同时在栈里很常见：工作台 → 打包 → BuildPage 看详情）。改用自带
   500ms Timer 纯读 BuildRunner 快照（build 里按需开/关 timer），与
   BuildPage/通知刷新互不干扰，三方看的是**同一会话**。
3. **零三方依赖**：pubspec/Manifest/gradle 解析全用 FsBridge.read + 正则，
   不引 yaml/xml 解析库（App 进程三方依赖归零是仓库原则）。

**互斥**：打包区检测 `otherBuilding`（正在构建的是其他工程）时显示
提示不允许再启动，防并发构建打爆 proot/gradle。

### 9.11 proroot 容器层接入实现（2026-09-19，v0.1.0-alpha.61/62）

`02-构建流程.md` §4 讲的是"为什么接"与"收益边界"；这里补**实现细节**，
因为 proroot 的原生化路径与既有 proot 有若干处"看起来能复用、实际不能"
的地方，踩过一次就会写成坑。

#### 1. 三条路径必须分开，不能合并

| 执行路径 | Kotlin 函数 | argv 形态 |
| --- | --- | --- |
| 容器 · proot | `buildProotCmd()` | `proot -0 -r <rootfs> -b /dev -b /proc -b /sys …` |
| 容器 · proroot | `buildProrootCmd()` | `libproroot.so -r <rootfs> -0 --link2symlink -w /root …` |
| 裸原生 · bare | `execBare()` | 宿主 `/system/bin/sh -c`，无容器 |

关键差异（不是"换个二进制"那么简单）：

- **`-r` / `-0` 顺序相反**。proroot 的启动器与 proot 的 CLI 是两套实现，
  参数顺序不同会导致启动器把 `-0` 当 rootfs 路径。**不能靠"反正都认
  -r"来合并**。
- **不需要 `-b /dev -b /proc -b /sys`**。proroot 的 bridge 组件会自动
  处理这些绑定；显式再加会重复绑定。反过来，**proot 那边必须显式绑**，
  所以这行代码不共享。
- **不需要 `PROOT_LOADER` / `PROOT_TMP_DIR` / `LD_LIBRARY_PATH`**。
  proroot 靠 `LD_PRELOAD` 做路径翻译，不是 ptrace，因此 proot 那两个
  坑（Bug 210 缺 libtalloc、Bug 211 临时目录硬编码 `com.termux`）
  **在 proroot 上不存在**。`applyProrootEnv(pb)` 是独立函数，不调用
  `libraryPath()`。
- **共享的部分照旧复用**：`/etc/resolv.conf` 幂等修正、
  `/etc/profile.d/foa-env.sh` 加载、"原生 gen_snapshot 落位才挂
  bionic 目录"——这三段逻辑与容器实现无关，两边都拼同一段字符串。

#### 2. `exec` / `execStream` 的分支写法

```kotlin
val built = if (proroot) buildProrootCmd(command) else buildProotCmd(command)
if (built.cmd == null) return built.error!!
val pb = ProcessBuilder(built.cmd)
if (proroot) {
    applyProrootEnv(pb)      // LD_PRELOAD 一套
} else {
    findLoader()?.let { ... } // PROOT_LOADER 一套
    ...
}
```

`bare` 在最前面就 `return execBare(...)` 分流掉了，所以到这一步
`proroot` 只会与"容器内的 proot"二选一。**Dart 侧保证 `bare` 与
`proroot` 不同时为真**（`build_runner.dart` 里 `final proroot =
!bare && layer == ContainerLayer.proroot`）——这是刻意的：
原生侧不该纠结"两个标志同时为真听谁的"。

#### 3. 状态查询与导入（SAF）

| Dart 方法 | 原生 handler | 说明 |
| --- | --- | --- |
| `prorootStatus()` | `prorootStatus` | 返回 `missing` / `notElf` 明细 + `abiOk` / `apiOk` |
| `prorootImport()` | `prorootImport` | `ACTION_OPEN_DOCUMENT_TREE` → `copyTree()` 递归 → `prorootInstall(stage)` |
| `prorootProbe()` | `prorootProbe` | 容器内真跑 `uname -a; echo FOA_PROBE_OK`，边读边判超时 25s |
| `prorootRemove()` | `prorootRemove` | 清空 `filesDir/proroot/`，返回删除数 |

两个设计要点：

- **导入必须是"用户选目录"而不是"我们代下载"**。许可禁止再分发，
  所以应用内不能下载这 5 个 `.so`。同时 Android 11+ 的
  `/data/data/<pkg>` 对文件管理器不可见，用户没有别的办法——SAF 是
  唯一通路。
- **`copyTree` 必须自己走 `DocumentsContract`**。tree URI 不像普通文件
  能一次 `openInputStream` 搞定；而且要**先拷到真实路径**再交给 proroot，
  因为 SAF 的 URI 在子进程里不可读（proroot 只认真实文件路径）。
  单文件读失败要吞掉继续（SAF 权限面常见），只要 `count > 0` 就继续。

#### 4. `ContainerLayer` 与 `BuildBackend` 是正交的

```
BuildBackend  决定「在不在容器里」   proot / termux
ContainerLayer 决定「进容器时用哪套」 proot / proroot
```

所以 `lib/toolchain/termux_backend.dart` 里把两者定义在**同一个文件**
但明确标注正交关系；`BuildRunner.start(..., layer:)` 里做 `!bare &&`
的合并。UI 上 termux 后端下会置灰 proroot 开关——但**置灰是提示，
不是约束**，Dart 侧仍然传 `false` 下去兜底。

#### 5. 排查入口

proroot 出问题的第一现场**几乎都是冒烟测试的输出**（不是 gradle 日志）：
`prorootProbe()` 会在容器里跑 `uname -a`，输出带 `FOA_PROBE_OK` 才算过。
如果冒烟测试不过，**不要去看构建日志**——容器层就没起来，构建日志
只会是一堆无关的连锁失败。
