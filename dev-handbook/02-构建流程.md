# 02 · 构建流程

> 本地构建管线全流程：rootfs 组装 → 工具链安装 → 构建执行 → 产物验证
>
> 目标：在手机的 proot Debian 沙箱内，用 Flutter 官方 linux-arm64 SDK 构建出可安装的 APK。

## 一、总体架构

```
App 进程 (Android)
    │
    ├─ 编辑器 UI (Flutter/Dart)
    │
    └─ 构建编排器 (Dart)
           │
           ▼  Process.start / 进程通信
    proot 沙箱 (Debian arm64)
           │
           ├─ JDK 17 (Temurin aarch64)
           ├─ Flutter SDK (linux-arm64 stable)
           ├─ Android cmdline-tools + platform (用户首次运行自取)
           ├─ aapt2 / zipalign (社区 ARM64 构建版，替换官方 x86_64)
           └─ Gradle + Dart/Flutter 构建链
```

## 二、rootfs 组装流程

### 组件清单与来源

| 组件 | 来源 | 许可证 | 分发方式 |
|---|---|---|---|
| Debian rootfs (minbase) | Debian 官方 / OCI 镜像 | 自由 | 首次启动下载 或 内置 |
| proot 二进制 | proot 上游 release | GPL-2.0 | 内置，关于页附源码链接 |
| Temurin JDK 17 aarch64 | Adoptium | GPLv2+CE | 首次构建下载 |
| Flutter SDK linux-arm64 | 官方 / 国内镜像 | BSD | 首次构建下载 |
| cmdline-tools | Google 官方 | Google SDK ToS | **用户首次运行自取** |
| android.jar (platform) | sdkmanager 安装 | Google SDK ToS | 用户自取 |
| aapt2 (arm64) | 社区 AOSP 交叉编译版 | Apache-2.0 | 内置 |
| zipalign (arm64) | 社区 AOSP 交叉编译版 | Apache-2.0 | 内置 |
| Gradle | services.gradle.org / 镜像 | Apache-2.0 | 首次构建自动下载 |

### 安装器执行顺序

```
1. 解压 / 下载 rootfs → filesDir/rootfs/debian/
2. 注入 proot 二进制 → filesDir/tools/proot
3. 写入环境变量脚本 → /etc/profile.d/flutter_env.sh
   - JAVA_HOME
   - ANDROID_HOME
   - PUB_HOSTED_URL
   - FLUTTER_STORAGE_BASE_URL
   - PATH
4. 下载 JDK → 解压到 /opt/jdk-17/
5. 下载 Flutter SDK → 解压到 /opt/flutter/
6. 注入 ARM64 aapt2/zipalign → /opt/android-tools/
7. 写入 ~/.gradle/gradle.properties（aapt2 override、JVM 参数）
8. 下载 cmdline-tools（用户确认后执行）
9. sdkmanager 安装 platform + build-tools（用户确认后执行）
10. flutter doctor --android-licenses（用户确认后执行）
```

### init.gradle 注入

位置：`~/.gradle/init.gradle` 或通过 `--init-script` 参数传递。

⚠️ **形态约束（Bug 426，2026-09-18）**：Flutter 新模板
`settings.gradle.kts` 走 **PREFER_SETTINGS** 仓库模式，拒绝任何

```groovy

beforeSettings { settings ->
    settings.pluginManagement.repositories {
        maven { url 'https://maven.aliyun.com/repository/public' }
        maven { url 'https://maven.aliyun.com/repository/google' }
        maven { url 'https://maven.aliyun.com/repository/gradle-plugin' }

        maven { url 'https://maven.aliyun.com/repository/public' }
        maven { url 'https://maven.aliyun.com/repository/google' }

```

（旧版 `allprojects + settingsEvaluated` 双保险形态只适用于没有
PREFER_SETTINGS 模板的老工程，对 Flutter 新模板是死路——见
04 号文档 Bug 426。）

位置：`~/.gradle/gradle.properties`

```properties
# 核心：强制使用本地 ARM64 aapt2
android.aapt2FromMavenOverride=/opt/android-tools/aapt2

# JVM 堆大小（按设备 RAM 动态调整，4GB 机设 1g，8GB+ 设 2g）

# 构建加速
org.gradle.caching=true
org.gradle.configuration-cache=true
org.gradle.parallel=true
org.gradle.daemon=true

# 只编 arm64（缩短构建时间）
flutter.targetPlatform=android-arm64
```

### 2.1 堆大小怎么定：两个上限，取小的那个（Bug 461）

「daemon disappeared」这个症状有**两个完全不同的成因**，处置相反：

| 成因 | 判据 | 处置 |
| --- | --- | --- |
| JVM 自身堆耗尽 | `free -m` 显示**大量 available** 却仍消失 | **加**堆 |
| cgroup OOM killer 击杀 | `cat /sys/fs/cgroup/memory.max` 已接近/触顶 | **减**堆 |

**定值公式**：

```
gradle 堆 + kotlin 堆 + 1.5g(元空间/线程栈/原生缓冲/JIT) < cgroup 上限
```

本沙箱（`memory.max` = **8 GiB**）取 `4g + 2g + 1.5g ≈ 7.5g`，留 0.5g 余量，
release 全量构建实测通过。

> ⚠️ **踩坑记录（alpha.62 出包）**：`gradle.properties` 曾被改成
> `-Xmx6g` + kotlin `-Xmx3g`（按 123GB 大机器定的），在本 8GiB cgroup
> 里必然超顶 → R8/dex 阶段 daemon 被击杀，报
> `Gradle build daemon disappeared unexpectedly`，
> `./gradlew assembleRelease` 跑满 2474s 后 FAILED。
>
> **教训**：
> 1. **"机器有多少内存"和"我能用多少内存"是两回事**——容器里以后者为准，
>    永远先 `cat /sys/fs/cgroup/memory.max`；
> 2. **同样的报错文案可能是相反的修法**，别按症状关键词条件反射；
> 3. **卡在构建后期（R8/dex）先怀疑内存**——AOT 阶段已过说明 Dart 侧没问题；
> 4. 失败后 `./gradlew --stop` + `pkill -f KotlinCompileDaemon` 释放内存，
>    **AOT 产物（`build/app/intermediates/flutter/release/*/app.so`）会保留**，
>    重试不会重跑昂贵的 Dart 编译，所以"加堆重试"代价很低，别急着清
>    `build/` 从头来。

## 三、构建命令

### Debug 构建

```bash

```

产物位置：`build/app/outputs/flutter-apk/app-debug.apk`


- 热重启：输入 `R` 回车；

## 五、构建编排器设计要点

1. **异步执行**：构建在独立 isolate 中运行，UI 不阻塞；
2. **实时日志**：stdout/stderr 逐行回传 UI，支持搜索；
3. **前台服务**：构建期间启动 Foreground Service，显示通知栏进度，降低被杀概率；
4. **Wake Lock**：构建期间持有 Wake Lock，防止休眠；
5. **可取消**：用户可随时终止构建（杀掉进程组）；
6. **构建缓存管理**：提供清理按钮，显示各缓存占用空间；
7. **内存压力监听**：监听 `onTrimMemory`，低内存时主动杀掉 Gradle daemon。

## 七、宿主架构 × 目标架构：交叉编译的关键概念（2026-09-16 实测定稿）

**核心结论：构建工具的宿主架构与产物目标架构是两个独立维度。x86_64 SDK 构建出 arm64 APK 是标准操作**（所有桌面开发者每天都在做），目标架构由 `--target-platform=android-arm64` / `abiFilters` 决定。

| 组件 | 敏感维度 | 说明 |
|---|---|---|
| aapt2 / zipalign | 仅宿主 | 原生二进制，处理资源，与目标 ABI 无关 |
| d8 / r8 / kotlinc / gradle | 均不敏感 | JVM 字节码，宿主 JVM 架构无关、产物架构无关 |
| gen_snapshot | **宿主 × 目标** | 在宿主架构上运行，生成目标架构的 AOT 机器码——SDK 按"宿主×目标"矩阵分发 |
| libflutter.so / libapp.so | 仅目标 | 直接从产物拷贝进 APK，本地无编译 |
| JDK | 仅宿主 | 手机上装 arm64 JDK，服务器上 x86_64 JDK |

**2026-09-16 实测事实（重要，修正旧表述）**：

1. **官方没有 linux-arm64 Flutter SDK**。releases_linux.json 中零 arm64 条目；`flutter_linux_3.47.4-arm64.tar.xz` 在 storage.googleapis.com 与 storage.flutter-io.cn 均 404。
   ⚠️ 修正：docs.flutter.dev/reference/supported-platforms 里 "Debian/Ubuntu Arm64 Supported" 指的是**部署目标**（在 arm64 Linux 上跑 Flutter 应用），不是开发宿主。
2. **aapt2 依然无官方 arm64 版**。最新稳定版 9.4.0-15978811 的 `linux` 分类器 jar 内含 x86-64 ELF；`linux-arm64` 分类器在 Google Maven 和阿里云镜像均 404。
3. Flutter 3.47.4 模板要求：`minSdk 24 / targetSdk 36 / compileSdk 36 / NDK 28.2.13676358`（NDK 仅原生插件需要）。

### 7.1 engine artifacts 仓库直测（2026-09-16，engine 06a2e2a1，HTTP 状态码）

URL 规律：`{FLUTTER_STORAGE_BASE_URL}/flutter_infra_release/flutter/{engine-hash}/android-{目标架构}-{mode}/{宿主}-{架构}.zip`

| 仓库路径（android-arm64-release 下） | google 官方 | flutter-io.cn 镜像 |
|---|---|---|
| `linux-x64.zip`（宿主 x64 的 arm64 目标 gen_snapshot） | **206 存在** | 206 存在 |
| `linux-arm64.zip` | **404 不存在** | 404 不存在 |
| `darwin-arm64.zip` | **404 不存在**（Apple Silicon 靠 Rosetta 跑 x64 包） | — |
| `windows-arm64.zip` | 404 不存在 | — |
| `dart-sdk-linux-arm64.zip`（全仓根路径） | **206 存在** | 206 存在 |

源码双重印证：`flutter_cache.dart` 的 `_linuxBinaryDirs` 硬编码 Android gen_snapshot 仅下载 `linux-x64` 宿主包；`artifacts.dart` 中 `darwin_arm64` 显式回退 `darwin_x64`（上游 TODO: flutter/flutter#152281）。**结论：Android gen_snapshot 全平台只有 x64 宿主版，属官方长期现状而非镜像缺失。**

**手机端 SDK 组装结论（实测版）**：dart-sdk 官方有 linux-arm64 版（206）✓；flutter_tools 是纯 Dart ✓；debug 引擎产物（`android-arm64/artifacts.zip`，libflutter.so debug 版）路径不带宿主目录、宿主无关 ✓；**唯一缺口 = arm64 宿主版 Android gen_snapshot（仅 release/profile 构建需要）**。debug 构建（JIT，kernel blob + frontend_server）全链路 arm64 原生可行，不受影响。

### 7.2 release 构建的 gen_snapshot 缺口：三条路线（Step 4 决策）

| 路线 | 做法 | 代价 | 备注 |
|---|---|---|---|
| A. 翻译执行（最快落地） | 内置 x64 gen_snapshot + qemu-x86_64 / box64 翻译运行 | AOT 编译慢 10~50 倍（小项目分钟级） | Termux/Armbian 社区验证过可行；注意 proot 内 qemu 依赖 ptrace |
| B. 社区/自编译 arm64 原生版 | 从 engine 源码在 arm64 上编译 gen_snapshot，随 App 内置（BSD 许可，附源码链接） | 一次性编译成本 + 每个 engine 版本跟进 | Termux-Flutter 项目已走此路线；产物单文件约 5~20MB |
| C. 分级构建 | 手机出 debug 包（原生快），release 引导桌面/云端 | 违背"本地优先"初衷 | 仅作兜底，不推荐主策略 |

建议：Step 4 先走 A 验证管线通，B 作为正式版目标（gen_snapshot 属 Flutter 引擎 BSD 产物，内置分发无许可证障碍）。

#### 7.2.1 兼容层的**两个层次**（Bug 428/429 教训，务必都覆盖）

x64 宿主工具分布在两个层次，**只包装一个必然出 SIGILL**：

| 层次 | 路径 | 内容 | 谁在用 |
|---|---|---|---|
| 引擎层 | `artifacts/engine/android-*/linux-x64/` | 每个 ABI 各一份 `gen_snapshot`（6 个） | release AOT 编译 |
| **顶层宿主层** | `artifacts/engine/linux-x64/` | `impellerc`、`font-subset`、`flutter_tester`、`gen_snapshot` + 3 个 `.so`（7 个） | **shader 编译**、字体子集化、测试 |

顶层宿主层的解析路径来自 `artifacts.dart` 的 `HostArtifact.impellerc`
→ `engineDir/<hostPlatform>/impellerc`，arm64 宿主解析为
`linux-arm64/impellerc`。**未包装则该文件不存在 → shader 编译 SIGILL**。

合计 **13 个** x64 宿主工具需全部纳入（可用
`assets/.../linux-x64/` 下 `x86_64 ELF`（魔数 `7f454c46` + `e_machine=3e`）
逐个比对 `linux-arm64/` 同名文件）。

> **核心原则：用全称命题，不用点名清单。**
> 正确的不变量是「对 `linux-x64/` 下**每一个** x86_64 ELF，
> `linux-arm64/` 里必须有同名 `#!` 转发脚本」——
> 这样 Flutter 新增任何宿主工具都自动纳入。逐一点名（"检查
> gen_snapshot 就够了吧"）在开放集合上必然持续漏，Bug 428→429
> 连续两次翻车就是这个原因。

### 7.2.2 PTY 中继器（可交互终端组件，Bug 430）

**这不是构建组件，但同样随 APK 分发，且构建期需重新编译**。

| 项 | 值 |
|---|---|
| 源码 | `app/platform/android/pty/foa_pty.c`（约 10KB） |
| 产物 | `app/assets/tools/foa_pty`（aarch64，纯 bionic） |
| 依赖 | 仅 `libc.so` + `libdl.so`（系统自带，零额外分发） |
| 构建 | `app/tools/build_pty_shim.sh [--verify]`（自动探测 NDK） |
| NDK | 仅**开发机**需要；用户设备完全不需要（已编译分发） |

**进程形态**：

```
Java(ProcessBuilder) ──pipe──▶ foa_pty ──pty──▶ proot / 宿主 sh
   写入=键盘           中继（真 tty）        子进程 isatty=真
   读出=屏幕
```

**为什么不能省掉它**：Android/JVM 没有 pty API，
`ProcessBuilder` 只能给单向管道；没有 tty 则 `vim`/`top`/`apt`
进度条/Ctrl+C/方向键历史/tab 补全全部失效。

**改这个文件前必读**（四个坑，全部有测试固化）：

1. **`c_cc[]` 必须显式赋值**——只设 `c_iflag`/`c_lflag` 而 `c_cc` 全零时，
   `stty -a` 会显示 `intr = <undef>`，`isig` 虽开着但内核认不出哪个字节
   是 Ctrl+C（现象：屏幕回显 `^C` 但 `sleep` 照睡）；
2. **`setsid()` 后不能再 `setpgid`**——会话首进程 `setpgid` 返回 EPERM，
   误当致命错误会 `_exit(120)`，表现为终端一启动就退出；
3. **父进程不能 `setpgid(child, child)`**——子进程成了进程组组长后，
   其 `setsid()` 会失败（POSIX 禁止），同样 rc=120；
4. **中继进程必须忽略 SIGINT/SIGQUIT/SIGTSTP**——否则按 Ctrl+C
   打的是中继自己，整个终端崩掉。

**窗口尺寸热更新**：master fd 只在 shim 手里，Java 改不了 winsize；
stdin 内联控制序列又会污染用户输入。解法 = 控制文件
`FOA_PTY_SIZE_FILE`（内容 `"<rows> <cols>"`）+ 主循环
`poll(..., 200)` 超时检查，变化即 `ioctl(TIOCSWINSZ)`。

### 7.3 双端构建心智模型（最终确认版）

**一句话**：宿主架构与目标架构是两个独立维度。APK 内部所有架构敏感组件都由**目标架构**决定，与"在谁的机器上、用什么架构的工具构建"无关——宿主架构不会泄漏进 APK。

**双端对照（本项目最终形态）**：

| | 服务器（bug 复现环境） | 手机（产品本体，proot rootfs 内） |
|---|---|---|
| 宿主工具架构 | x86_64（官方 SDK 开箱即用） | arm64（dart-sdk-linux-arm64 + arm64 JDK + 社区 arm64 aapt2） |
| 构建方式 | 交叉编译 | 原生编译（除 release 的 gen_snapshot 缺口） |
| gen_snapshot（release） | x86_64 宿主版，原生直跑 | qemu-x86_64/box64 翻译 x64 版，或社区 arm64 版（见 7.2） |
| 产物 | arm64 APK | arm64 APK（同一目标） |

**APK 内部架构分布**：

| APK 内组件 | 架构 | 来源 |
|---|---|---|
| `lib/arm64-v8a/libflutter.so` | arm64 ELF | 引擎产物**直接拷贝**进 APK，本地不编译 |
| `lib/arm64-v8a/libapp.so` | arm64 AOT 机器码 | gen_snapshot 生成（debug 构建为 kernel blob，无此文件） |
| `classes.dex` | 架构无关（JVM 字节码） | kotlinc/javac + d8 编译，跑在任何架构的 JVM/ART 上 |
| `res/`、`resources.arsc`、`assets/` | 架构无关 | aapt2 处理 |

**易混淆点澄清**（2026-09-16 确认）：

1. "x86_64 SDK 构建 arm64 APK" 描述的是**服务器侧**；手机侧用的不是 x86 SDK，而是全 arm64 工具链（工具本身要在手机 CPU 上跑）。
2. "从 APK 内部逻辑层开始一律 arm64" 方向正确但更彻底：APK 里**所有**架构敏感组件都是 arm64（dex 与资源本就架构无关），且这一点**与构建宿主无关**——同参数下服务器与手机构建出的 APK 架构与管线一致，这是服务器能替手机复现构建逻辑类 bug 的根基（见第八节 Tier 1/2）。
3. 交叉编译不是本项目特权：所有桌面开发者每天都在用 x86_64 Mac/PC 构建手机 arm64 APK，gen_snapshot 本体就是"x86-64 ELF、自报 `linux_simarm64`"（工具 3 的双维度验证法见 04 号文档排查工具箱）。

## 九、镜像选择策略（App 端下载器设计，Step 3/4 实现）

**不要用 ICMP ping**：移动网络常丢 ICMP，且 ping 延迟 ≠ 下载吞吐（高延迟卫星链路可能带宽巨大）。正确做法：

1. **HTTP 并发竞速**：对所有候选镜像同时发起 `Range: bytes=0-65535` 的小块 GET，用"首字节时间 + 64KB 传输完成时间"排序，取最快；
2. **失败降级**：竞速全部失败时按预设优先级顺序串行重试；
3. **会话内缓存**：测速结果缓存至进程生命周期内，避免每次下载重复测；镜像异常（连接重置、超时）时立即降级并标记冷却（10 分钟内不再选它）；
4. **分级镜像表**（按组件类型，App 内置可云端更新）：

| 组件 | 镜像优先级（国内） |
|---|---|
| Flutter SDK / 引擎产物 | storage.flutter-io.cn → storage.googleapis.com |
| Pub 依赖 | pub.flutter-io.cn → pub.dev |
| Gradle 发行版 | mirrors.cloud.tencent.com/gradle/ → services.gradle.org |
| Maven 依赖（AGP 等） | maven.aliyun.com/repository/google → dl.google.com |
| Android SDK 组件 | ⚠️ 待定：dl.google.com 国内不可达，腾讯镜像 /AndroidSDK/ 覆盖范围需实测（Step 6 解决） |

5. **校验**：所有下载附 SHA-256（清单云端下发），块级断点续传。

## 十、Web 实时预览（alpha.57，2026-09-19）

### 定位

编辑器页新增「实时运行预览」：把当前项目以 **web 形态**在后台运行，
改代码 → 热重载即时生效，把「改一点 → 出包 → 装包 → 看效果」的
5-10 分钟循环压成 **1-5 分钟首次编译 + 秒级热重载**。面向开发期临时验证，
不替代真机出包（最终行为仍以 APK 为准）。

### 原理：为什么 web 是全工具链里最轻的路径

| 对比项 | APK 构建 | Web 预览 |
|---|---|---|
| Dart 编译 | AOT gen_snapshot（x64 真身 + qemu 转发，Bug 428/433/449 全家桶） | DDC/kernel（dart 直接跑，pub get 同款已验证链路） |
| Gradle / NDK / SDK | 全套重器 | **完全绕开** |
| 常驻性 | 跑完即退 | `flutter run -d web-server` 常驻进程 |

### 热重载协议（不依赖终端交互）

flutter_tools 注册了 POSIX 信号处理：**SIGUSR1 = 热重载，SIGUSR2 = 热重启**。
启动命令先 `echo $$ > /tmp/foa_web_preview.pid` 再 `exec flutter run`
（exec 是进程内替换，pid 不变）→ 之后任意时刻
`kill -USR1 $(cat /tmp/foa_web_preview.pid)` 即触发热重载——
走普通 exec 通道，**全程无 PTY**。

### 关键设计决策

1. **端口固定 8090** → URL 恒定（`http://127.0.0.1:8090`），
   浏览器直达不依赖日志解析；proot 不隔离网络命名空间，
   Android 浏览器与容器共享 localhost。
   （注：**alpha.60 更正**——此前写的"App 自身侧不能探测该端口"
   是**错的**。见下方 alpha.60 增补第 1 条：Dart `dart:io` 的
   HttpClient 走 NDK 原生 socket，不受 targetSdk 28 明文策略约束，
   现已成为 ready 判定的**旁路证据**。）
2. **与构建互斥**：两者共用 Flutter 启动锁（bin/cache/lockfile），
   并发必卡「Waiting for another flutter command」→ 双向检测拒绝。
3. **启动命令内联自愈**：残留孤儿会话清理（防端口占死）→ 版本检查
   stamp（Bug 436）→ 缺 `web/` 自动 `flutter create --platforms=web --no-pub`
   → pub 三源轮换（Bug 423）→ 转发层再断言（Bug 433）→ exec flutter run。
4. **会话与页面解耦**（照 BuildRunner 单例模式）：退出控制台页/锁屏/
   切浏览器，预览照跑（前台服务 BuildNotify 保活）；编辑器顶栏按钮
   运行中变**直达热重载键**。
5. **边界**：termux 后端第一版不开放（bionic flutter web 未验证）；
   execStream 超时 7200s = 预览最长 2 小时，到时重启即可。

4. **容器层加速（proroot）**（`lib/toolchain/proroot_option.dart`，
   工具链页「x64 兼容层(QEMU)」卡片下方）：**alpha.61 起已接入可用，
   但默认仍是 proot**。交互顺序被刻意设计成
   「导入二进制 → 冒烟测试 → 才允许开启」——不是仪式感，而是因为
   与 Debian rootfs 的组合未验证过，直接开开关去构建，失败了用户
   只会看到一堆 gradle 报错，根本定位不到是容器层的问题。

   实现要点：
   - **落位目录 `filesDir/proroot/`**（不是 jniLibs）：jniLibs 的 `.so`
     会被系统当"库"校验，而 5 个文件里只有 `libproroot.so` 是启动器，
     混进去反而要靠 rename 绕过（现有 proot 就这么做的，代价是名字
     对不上、排查困难）。
   - **导入走 SAF**：Android 11+ 的 `/data/data/<pkg>` 对文件管理器
     不可见，用户**没有别的办法**把文件放进去。所以原生侧开了
     `ACTION_OPEN_DOCUMENT_TREE`，递归拷贝后按文件名认领，
     并立刻验 ELF 魔数（用户很容易误选 zip 或非 arm64 构建）。
   - **冒烟测试必须真跑**：`prorootProbe()` 在容器里执行
     `uname -a; echo FOA_PROBE_OK`。只检查"文件在不在"判断不了兼容性。
   - **argv 是独立实现**（`buildProrootCmd()`）：proroot 的
     `-r <rootfs> -0` 顺序与 proot 的 `-0 -r <rootfs>` 不同，且不需要
     显式 `-b /dev -b /proc -b /sys`（bridge 组件自动处理）。
     与 proot 路径一致的部分仍复用：resolv.conf 幂等修正、
     foa-env.sh 加载、"原生 gen_snapshot 落位就挂 bionic 目录"。
   - **ContainerLayer 与 BuildBackend 正交**：前者决定"进容器时用哪套
     路径翻译"，后者决定"在不在容器里"。termux 裸原生根本不进容器，
     此时 layer 无意义（Dart 侧传 `proroot: false` 下去，
     免得原生侧纠结两个标志同时为真怎么办）。

   仍然如实告知用户的几点（卡片上原样保留）：
   - **收益边界**：proroot 用 LD_PRELOAD + 二进制补丁替代 proot 的
     ptrace，省掉每次系统调用的两次上下文切换——但 FOA 构建慢的大头是
     **QEMU 指令翻译**（gen_snapshot / gradle / aapt2 都是 x64
     二进制）与 dart/gradle 自身计算，**这两项 proroot 零改善**。
     有感的是 I/O 密集操作（apt / tar / 海量小文件）。
   - **不是换二进制就能切**：启动器是 `libproroot.so -r <rootfs> -0
     --link2symlink -w /root …`，与现有 `proot -0 -r … -b /dev …` 的
     argv 顺序/取值不一致 → **已新开一条执行路径** `buildProrootCmd()`
     （不改 `buildProotCmd()`，两者并存互不影响）。
   - **环境不匹配**：官方要求 **Ubuntu arm64 rootfs**，本项目是
     **Debian 12 bookworm**——未验证组合，**这正是冒烟测试存在的理由**。
   - **许可**：Proprietary，源码未公开（无法自审自修），禁止分发
     修改过的二进制。卡片上逐字照抄原文并给出仓库地址
     `https://github.com/coderredlab/proroot`。
     **本项目不代为分发**这 5 个 `.so`——用户自行获取后用「导入 proroot」
