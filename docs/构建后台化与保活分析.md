# 构建任务的后台化与保活分析

> 面向问题：「能不能用 task 单独把进程构建避免长时间占用主界面（是否需要 app 申请通知权限保活）」
> 日期：2026-09-17 ｜ 结论：**通知权限不是当前瓶颈**，真正的瓶颈是原生侧单线程 executor。

---

## 一、先纠正一个最容易走错的方向：通知权限解决不了"占用主界面"

用户问题的隐含因果是：**后台任务 ↔ 需要通知保活**。这个关联在普通 App 上成立，但在 FOA 上，顺序是反的。

### 现状核查

```kotlin
// MainActivity.kt:66
private val executor: ExecutorService = Executors.newSingleThreadExecutor()
```

```kotlin
// MainActivity.kt:82-84  所有 MethodChannel 调用都进这一个线程
MethodChannel(...).setMethodCallHandler { call, result ->
    executor.execute {          // ← 单线程队列
        try { when (call.method) { ... } }
    }
}
```

**这是"长时间占用主界面"的真正根因，而且和通知权限毫无关系。**

`execStream` 在 `executor` 上跑的是 **`pb.start()` 本身**——启动进程很快，之后读取和 `waitFor` 都甩到了新建的 `Thread`（`MainActivity.kt:590`）。所以：

- 构建**不会**堵住 executor 的队列（`execStream` 秒级返回）；
- 但构建期间用户做的**其他所有 proot 调用**（文件浏览器目录列举、编辑器格式化、终端命令、`envInfo`）
  都排在**同一个单线程 executor** 上，要等前面排队的调用完成。

所以用户体感到的"卡"有两个不同来源，必须分开治：

| 症状 | 根因 | 通知权限能治吗 |
|---|---|---|
| 界面切走了、构建被系统杀了 | 进程优先级 / 后台限制 | ❌ 不能（见 §三） |
| **界面还在、但操作别的功能要等很久** | **单线程 executor 排队** | ❌ 完全无关 |

用户描述的"长时间占用主界面"，从措辞看更接近第二种。这个用通知权限是**百分之百治不好**的。

## 二、任务 1 交付：进度条（已实现）

用户第一项需求"添加进度条显示当前构建进度，不然容易让用户以为卡死"已落地，见：

- `app/lib/toolchain/build_progress.dart`（新增，纯逻辑，含 12 项单测）
- `app/lib/toolchain/build_page.dart`（改造 `_buildProgressPanel()`）
- `app/test/build_progress_test.dart`（新增）
- `app/build_progress_preview.html`（四态视觉预览）

### 设计要点（为什么不是一条普通进度条）

`flutter build apk` **不输出百分比**，所以进度只能推断。三个关键决策：

**① 阶段识别 + 阶段内插值，而不是匀速动画。**
日志关键词映射到 9 个阶段（准备 → 解析依赖 → 配置 Gradle → Dart 内核 → AOT → 资源 → dex → 打包 → 校验）。
阶段权重按真机实测的耗时占比分配——Gradle 配置和 aapt2 资源编译（都在 qemu 里跑）拿了大头。

**② 阶段内用 `1 - e^(-t/τ)` 指数渐近，不用线性。**

```dart
// τ = 12s：约 12s 走完 63%，36s 走完 95%
final target = 1.0 - math.exp(-elapsed / tauMs);
_intraStage = target.clamp(0.0, 0.92);   // 封顶 92%，永不顶到阶段上限
```

线性插值一旦预估偏短就会顶到上限然后"僵住"——**又变成用户以为卡死**。指数渐近永远在动，越接近上限越慢，视觉上更接近真实。

**③ 只有"退出码 0 **且** 产物文件确实存在"才授予 100%。**
不会出现"进度条走满但其实没出包"的假成功。失败/取消时进度**冻结**在真实中断点并变红，而不是继续爬。

配合的面板还给了三重"没卡死"证据：百分比 + 阶段名 + **每秒跳动的已用时间**。
另外从日志里识别已知错误模式（`Exec format error` / 缺库 / 磁盘满 / 依赖下载失败 / 快照不兼容），
翻译成可执行建议显示在进度条下方，省得用户去翻 1000 行日志。

## 三、任务 2 交付：后台任务与保活 —— 通知权限到底要不要

### 3.1 结论先行

| 方案 | 是否可行 | 说明 |
|---|---|---|
| **前台服务 + 通知** | ❌ **本项目走不通** | `targetSdk = 28` 下 `startForegroundService` 的 5 秒超时规则与 Android 8.0 起的通知渠道强制要求叠加，行为高度依赖厂商 ROM |
| **`POST_NOTIFICATIONS` 权限** | ❌ **当前拿不到** | 见 §3.2，这是 `targetSdk 28` 的直接副作用 |
| **`PARTIAL_WAKE_LOCK`** | ✅ **推荐** | 免权限、作用精确、与通知无关 |
| **`FLAG_KEEP_SCREEN_ON`** | ✅ **推荐（可选）** | 免权限，构建中亮屏 |

### 3.2 关键发现：`targetSdk 28` 决定了通知权限**根本不会弹**

这是本次分析最重要的技术结论，容易被忽略：

`POST_NOTIFICATIONS` 是 **Android 13（API 33）** 引入的运行时权限。
而 Android 的运行时权限机制有一条基本规则：**应用只会被要求授予「其 `targetSdk` 及以下」引入的运行时权限。**

本项目 `targetSdk = 28`（这是 W^X 的硬性要求，不能改，见 Bug 401/402）：

```
targetSdk 28  <  Android 13 (33)  →  系统不会向用户请求 POST_NOTIFICATIONS
                                   →  清单里声明了它也拿不到
                                   →  通知被系统静默丢弃（连"通知被拒"的提示都没有）
```

**所以：申请通知权限在当前架构下是无效操作。** 声明了不报错、不弹窗、不生效——
这正是最坏的失效模式：开发者以为有了保活，实际什么都没有。

> 补充：`targetSdk 28` 还会让应用在未来 Android 版本上落入各种兼容性开关（如通知渠道强制、后台启动限制），
> 行为越来越依赖 ROM。这也再次说明：**真正的技术债是 `targetSdk 28`，不是 qemu，也不是保活。**

### 3.3 那构建会被杀吗？—— 实测结论：风险不高，但确实存在

构建以 proot 子进程形式存在，属于应用进程组。被杀的条件通常有三类：

| 触发条件 | 本项目是否命中 | 缓解手段 |
|---|---|---|
| 用户手动「强行停止」 | 任何方案都无解 | 无（用户意图） |
| 系统内存压力 LMK | 构建期内存占用高（gradle + R8），**有风险** | 加 `oom_score_adj` 不可控；降低 `-Xmx`（现为 1536m） |
| 长时间处于后台被判定可回收（App Standby） | 屏幕关闭后进入 Doze 时**有风险** | `PARTIAL_WAKE_LOCK` |

### 3.4 推荐落地方案（免权限、改动小、风险低）

#### 方案 A：`PARTIAL_WAKE_LOCK`（**核心，必做**）

```kotlin
private var buildWakeLock: PowerManager.WakeLock? = null

/** 构建开始：CPU 保持唤醒（屏幕可以关，CPU 不能睡）。 */
private fun acquireBuildWakeLock() {
    if (buildWakeLock != null) return
    val pm = getSystemService(Context.POWER_SERVICE) as PowerManager
    buildWakeLock = pm.newWakeLock(
        PowerManager.PARTIAL_WAKE_LOCK,
        "foa:build"
    ).apply {
        setReferenceCounted(false)
        acquire(3 * 60 * 60 * 1000L)   // 上限 3h，与 execStream 的 7200s 超时对齐
    }
}

/** 构建结束/取消/异常：必须释放，否则耗电。 */
private fun releaseBuildWakeLock() {
    buildWakeLock?.let { if (it.isHeld) it.release() }
    buildWakeLock = null
}
```

挂载点：`execStream` 成功后 `acquire`，`execStreamStop` / 读取线程 `finally` 里 `release`。

**`PARTIAL_WAKE_LOCK` 不需要任何权限**（`WAKE_LOCK` 是 normal 级权限，安装即授予，无需运行时请求）。

#### 方案 B：`FLAG_KEEP_SCREEN_ON`（可选，但用户体验好）

构建期间屏幕常亮，用户盯着进度条时不会被息屏打断：

```kotlin
// 前台服务用不了，退而求其次：构建期间让窗口保持常亮
runOnUiThread {
    if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.O_MR1) {
        setTurnScreenOn(true)
    }
    window.addFlags(WindowManager.LayoutParams.FLAG_KEEP_SCREEN_ON)
}
// 构建结束：window.clearFlags(FLAG_KEEP_SCREEN_ON)
```

同样**免权限**。

#### 方案 C（下一步，非本次范围）：**拆掉单线程 executor** —— 这才是治本

回到 §一 的根因。既然 `targetSdk 28` 把前台服务之路封了，正确的做法是**让构建不再拖累 UI**：

```kotlin
// 现状：单线程队列，构建期间所有 proot 调用排队
private val executor: ExecutorService = Executors.newSingleThreadExecutor()

// 建议：固定线程池，长任务互不阻塞
private val executor: ExecutorService = Executors.newFixedThreadPool(4)
```

但**不能直接改**，有三个约束要一并处理：

1. **顺序依赖**：`installRootfs` 等操作假定了串行语义（例如 rootfs 未装完时不能执行命令）。
   改多线程后需引入显式的状态门禁，而不是靠队列顺序兜底。
2. **`execStreamPoll` 的内存可见性**：缓冲已经是 `synchronized(sc.lock)` 保护的（`MainActivity.kt:622`），
   并发安全，这点没问题。
3. **`pendingPickResult` / `pendingInstallResult` 等挂起字段是单例**，并发调用同一方法会互相覆盖。
   需要改成按 requestCode 索引的 Map。

**建议把它作为独立任务推进**（风险明确、改动面涉及 5 处原生状态），不要和本次进度条改动混在一起。

#### 方案 D（远期）：通知中心的前台服务

只有当项目**放弃 `targetSdk 28`** 之后才成立。届时可以：

1. 引入 `compileSdk 36` 下的前台服务，`foregroundServiceType="dataSync"`；
2. 清单声明 `POST_NOTIFICATIONS`，运行时请求；
3. 通知里放"取消构建"按钮，用户锁屏也能中止。

**但这条路的前提是先解决 W^X**（见 §四），顺序不能反。

## 四、顺带说明：为什么 `targetSdk 28` 是总闸

本次分析反复撞到同一个墙，值得单独说清：

```
targetSdk 28
  ├── 必需：Android 10+ 禁止 targetSdk>=29 应用 execve 数据目录二进制（W^X）
  │         └── 这是 FOA「真机本地构建」的地基，不能动
  ├── 副作用 1：拿不到 POST_NOTIFICATIONS → 通知保活不可用
  ├── 副作用 2：前台服务受 Android 8 通知渠道规则约束 → 行为依赖 ROM
  └── 副作用 3：无法上架 Google Play（已知且已接受）
```

**结论：只要 FOA 坚持"应用内真机本地构建"，`targetSdk 28` 就锁死了，通知方案就一直在门外。**
所以保活只能靠 `PARTIAL_WAKE_LOCK` 这类免权限机制，这是**架构决定的必然选择**，不是取舍。

### 关于"是否需要申请通知权限"的最终答复

> **不需要，而且在当前架构下也申请不到。**
> `targetSdk = 28` 低于 Android 13（API 33），系统不会请求 `POST_NOTIFICATIONS`，
> 声明它只会造成"以为有保活、实际没有"的静默失效。
> 构建保活应当用**免权限的 `PARTIAL_WAKE_LOCK`**（CPU 不断电）配合可选的
> `FLAG_KEEP_SCREEN_ON`（构建中亮屏）；而"占用主界面"的问题，
> 根因是原生侧 **单线程 executor**，需要单独重构，与权限无关。
