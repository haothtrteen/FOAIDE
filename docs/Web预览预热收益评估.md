# Web 预览预热收益评估

> 问题：App 启动时预编译一次「空白项目」的 web 产物，后续项目的热重载是否能直接复用，
> 从而变快？
>
> 结论：**不能复用，收益接近零。不建议做。**
> 但排查过程中发现真正能提速的两个点（见 §4），代价小、收益实。

评估日期：2026-09-19（alpha.62 周期）
相关代码：`lib/editor/web_preview_service.dart`、`lib/editor/web_preview_page.dart`

---

## 1. 先厘清"热重载"在这条链路上到底是什么

FOA 的 Web 实时预览不是 Flutter 官方的 hot reload（那是 VM Service 的
能力，需要 `flutter run` 常驻进程）。这里实现的是：

```
flutter build web --debug  →  产出 build/web  →  静态服务器  →  WebView 加载
```

每次源码改动后重新构建一次，然后让 WebView 重新加载。所以
**"热重载"的真实语义是"重新跑一遍 build web"**。想让它变快，
唯一有效方向是缩短 `build web` 的耗时。

## 2. 预热思路为什么无效：产物是项目专属的

"预编译一个空白项目，后续复用它的 DDC 产物"这个思路成立的前提是
**不同项目的 DDC 产物可以互换**。实际上不能：

| 维度 | 是否项目相关 | 说明 |
|---|---|---|
| Dart 源码 | ✅ 完全相关 | 每个项目的 `lib/` 完全不同 |
| package 依赖图 | ✅ 完全相关 | `package_config.json` 由各自 `pubspec.yaml` 生成 |
| kernel 快照（`.dill`） | ✅ 完全相关 | DDC 产物的输入就是它 |
| 资源清单 | ✅ 相关 | 各自的 `pubspec.yaml` assets 段 |
| Flutter engine 的 web 运行时（dart_sdk.js 等） | ❌ 不相关 | **这个才是唯一可复用的部分** |

也就是说，一个空白项目的 `build/web` 里，**只有 Flutter 引擎那一坨
与项目无关**，其余全是该项目的代码。而复用不能只复用一半——
DDC 产物之间是引用关系，混用会得到"找不到模块"的运行时错误。

## 3. 量化：就算能复用，能省多少

在容器里实测一次 `flutter build web --debug` 的耗时分布
（arm64 + QEMU 翻译 x64 工具链）：

| 阶段 | 占比 | 是否项目相关 |
|---|---|---|
| Flutter 引擎 web 运行时准备（拷 `dart_sdk.js` 等） | ~8% | ❌ 可复用 |
| `pub get` / 依赖解析 | ~12% | ✅ |
| **Dart → kernel（frontend_server）** | ~35% | ✅ |
| **DDC 模块编译** | ~35% | ✅ |
| 资源拷贝与收尾 | ~10% | ✅ |

**可复用的只有第一行，约 8%。** 而且这 8% 里真正慢的是一次
`cp` 操作——在 Android 内部存储上，几十 MB 的拷贝是秒级，
不是分钟级。

**结论**：花力气做一套"空白项目预编译 + 产物缓存 + 失效检测"的机制，
换回个位数百分比的收益，且要承担"缓存不一致导致玄学失败"的风险。
**性价比不成立。**

## 4. 真正值得做的两件事

排查过程中发现了真正的瓶颈，按性价比排序：

### 4.1 复用 `pub get` 结果（收益 ~12%，代价极小）

`pub get` 在每次构建时都会重新解析依赖并检查 `.dart_tool/package_config.json`。
如果 `pubspec.yaml` 的 mtime 与 `pubspec.lock` 一致、且
`package_config.json` 存在，就可以跳过。

- **代价**：一次 `stat` 比较，几行代码。
- **风险**：`pubspec.yaml` 被外部改动而 mtime 未变（极少见，git checkout
  会更新 mtime）。已有 `pubspec.lock` 作为第二重校验。
- **状态**：本轮未实施（不在 14 项需求内），建议下一轮做。

### 4.2 去掉 `--debug`，改用 `--profile` 或只跑一次 DDC（收益待测）

`flutter build web --debug` 会开启 DDC 的调试能力（source map、
热重载支持），比 `--release` 慢不少。预览场景其实不需要完整调试能力。

需要实测确认：`--profile` 在 web 上是否支持、产物体积与加载速度的
权衡。**未验证，不下结论。**

### 4.3 明确不做的：把 engine 运行时单独抽出来复用

技术上可行（把 `dart_sdk.js` 等固定产物缓存在
`/opt/foa-web-cache/`，构建后软链过去），但：

- 需要处理 Flutter SDK 升级导致缓存失效；
- 需要确认 DDC 产物**不**内嵌 engine 的绝对路径（否则软链位置必须完全一致）；
- 收益上限就是 §3 那 8%，其中大部分还是 `cp`。

**风险高于收益，明确不做。**

## 5. 总结

| 方案 | 收益 | 风险 | 结论 |
|---|---|---|---|
| 启动时预编译空白项目，后续复用 | ≈0（产物不可互换） | 高（缓存不一致） | **不做** |
| 复用 `pub get` 结果 | ~12% | 低 | 建议下一轮做 |
| 换 `--profile` 或精简 DDC | 待实测 | 中 | 需先测 |
| 单独缓存 engine 运行时 | ≤8% | 中 | 不做 |

**回到用户的原问题**："启动时预编译空白项目 web，后续从空白项目热重载
是否更快"——**答案是不更快**。空白项目的产物除了引擎运行时之外，
对新项目毫无用处；而引擎运行时本来就不需要"预编译"，它只是拷贝。

真正拖慢预览的是**每次都要重新把该项目的 Dart 代码编译两遍**
（kernel + DDC），这部分**没有捷径**——除非改掉"每次重新构建"这个
根本设计（比如接 VM Service 做真正的 hot reload，那是另一个量级的
工程，也不在本次需求范围内）。

## 6. 补记（2026-09-20，alpha.64 周期）：为什么 web 比 APK 构建还慢

用户实测反馈："**apk 6 分钟就好了，web 要十多分钟**。" 这个对比反直觉
——APK 要过 AOT、Gradle、R8、aapt2 一堆重活，web 只是编 Dart 代码。

**答：两者被 QEMU 翻译的"代码量"差异极大，瓶颈根本不在同一层。**

FOA 的 x64 兼容层（`lib/toolchain/qemu_compat.dart`）把
`bin/cache/dart-sdk/bin/dart`、`linux-arm64/gen_snapshot` 等
**全部是 x86_64 ELF** 的工具，靠转发脚本进 qemu-user 执行
（官方没有 linux-arm64 版工具链，`artifacts.dart` 里挂着
`flutter/flutter#152281` 的 TODO）。

| | APK 构建 | Web 预览 |
|---|---|---|
| Dart 前端（kernel） | 走一次 | 走一次 |
| **后端编译** | **`gen_snapshot`**（x64，**过 qemu**） | **DDC `dartdevc`**（Dart 写的工具，**同样过 qemu**） |
| 后端产物形态 | AOT 快照，**一次成型** | **DDC 按模块产出大量 `.js` + `.map`，逐模块翻译** |
| Gradle / R8 / aapt2 | 有，但**是 JVM 宿主原生代码** | 无 |

**关键**：
- `gen_snapshot` 是**一次性整体编译**——单次重，但只做一次。
- DDC 是**为开发期增量编译设计的**：把应用切成大量细粒度模块分别编译，
  还要产出 source map、保留调试信息。这个"细粒度 × 带调试信息"的
  组合在被 QEMU 逐条翻译时被**放大**了——模块多、每个模块都要起一次
  编译动作、还有大量元数据 I/O。
- **Gradle/R8 那些"重活"其实不慢**，因为它们在 JVM 里跑，
  是**宿主原生代码，根本不经过 qemu 翻译**。

即：**APK 赢在"后端只干一次"，web 输在"后端要干很多次、每次都过 qemu"。**

### 6.1 与 §1–§5 的关系

§1–§5 的结论（"预热复用产物"不成立）**依然完全有效**，而且理由更硬了：
DDC 产物里的模块引用是**硬编码路径**的，跨项目混用会直接运行时报
"找不到模块"。§3 里"引擎运行时 ~8% 可复用"的方向没错，但实际可复用面
比 8% 更小。

### 6.2 对 proroot 的明确结论（重要）

**不要指望 proroot 提速 web 预览。** proroot 优化的是**容器层**
（`LD_PRELOAD` 路径翻译替代 ptrace 的两次上下文切换）；而 web 预览的
瓶颈是 **QEMU 指令翻译**——这两层在栈上完全不相干。
UI 文案（`ProrootOption.gainNote()`）已经写对了这一点，保留不动。

> **补记（见 Bug 471）**：本节结论与 proroot 当时**能不能跑起来**
> 是两个独立的问题。本节说的是"**就算它能跑，也不提速 web**"；
> 而 Bug 471 说的是"**它当时压根跑不起来**"——我们跟着上游 `main`
> 拿到了要求 glibc 2.38 的 v1.2.8，而我们 rootfs 是 2.36。
> 两条结论不冲突，但要注意别把它们混起来：**修好 Bug 471 之后，
> 本节结论依然成立**，proroot 仍然不该被期待能加快 web 构建。

### 6.3 真要提速的唯一有量级收益的方向

改掉"每次重新构建"这个设计本身 —— 接 VM Service 做**真正的 hot reload**
（增量 patch，而不是整包重编）。那是另一个量级的工程，
且需要 `flutter run` 常驻进程 + DDC 的增量服务配合。

短期可做的仍是 §4.1 / §4.2 那两项，合计预期**远不足以**让
"十多分钟"变成"一两分钟"——**不要在 UI 上暗示用户会变快**。

> **方法教训**：比较两条性能路径前，先确认它们的瓶颈在不在同一层。
> "更重的构建更快"这种反直觉现象，几乎总是因为——
> **你以为的重活根本没在慢的那一层上。**
